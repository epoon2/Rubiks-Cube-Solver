# Rubik's Cube Solver

A program that can represent, manipulate, and solve Rubik's Cubes.

## What works today

- A 3x3 cube represented as six 3x3 faces of stickers, with the six face turns
  in standard notation (`F`, `F'`, `F2`, and so on for `B`, `U`, `D`, `L`, `R`).
- A cubie-level representation of the same cube, tracking where the eight
  corner and twelve edge pieces are and how they are twisted.
- Three solvers:
  - **Breadth-first search**, which solves cubes up to about five moves from
    solved and nothing beyond.
  - **A\***, with a misplaced-sticker heuristic. That heuristic is not
    admissible, so this is really a greedy search: it goes a little deeper
    than BFS and its answers are not guaranteed to be the shortest.
  - **Kociemba's two-phase algorithm**, which solves any legal cube in around
    a twentieth of a second.
- A benchmark harness comparing the three.
- A 2D matplotlib view of the cube as an unfolded net.

## Why the first two solvers are not enough

A 3x3 cube has 4.3x10^19 states and a branching factor of 12 for quarter
turns, so searching outward from the solved state runs out of time and memory
after a handful of moves. `python/src/depth_wall.py` measures exactly where
that happens. Three random scrambles per depth, 60 seconds and 2 GB per run,
with each solver told the exact depth to search to:

| Scramble depth | BFS solved | BFS median | A\* solved | A\* median |
| -------------- | ---------- | ---------- | ---------- | ---------- |
| 3              | 3/3        | 0.11s      | 3/3        | 0.01s      |
| 4              | 3/3        | 0.78s      | 3/3        | 0.03s      |
| 5              | 3/3        | 3.17s      | 3/3        | 0.95s      |
| 6              | 1/3        | 20.19s     | 3/3        | 3.26s      |
| 7              | 0/3        | timeout    | 2/3        | 13.15s     |
| 8              | 0/3        | timeout    | 3/3        | 12.14s     |

A real scramble is around eighteen moves from solved, so neither solver is
within orders of magnitude of one.

## How the two-phase solver gets past that

It does not search the cube's states at all. It searches two much smaller
quotients of them, through the subgroup `G1 = <U, D, R2, L2, F2, B2>`:

- **Phase 1** orients every corner and edge and puts the four middle-slice
  edges back in the middle slice. Only three coordinates matter (corner
  orientation, edge orientation, slice location), and twelve moves always
  suffice.
- **Phase 2** solves the cube using only G1's own moves, which can no longer
  disturb orientation. Three more coordinates cover it (corner permutation,
  U/D edge permutation, slice edge order), and eighteen moves always suffice.

Each phase runs IDA\* against exact distance tables for pairs of coordinates,
so the heuristics are admissible and the searches are short. The tables come
to about 8 MB; they are generated by `python/src/solvers/kociemba_tables.py`
in under two seconds on first use and cached on disk afterwards. Nothing
binary is checked in.

The price is that two-phase solutions are not optimal. The detour through G1
costs a few moves, so solutions come out in the low twenties against an
optimal solve of around eighteen.

Measured over 100 random 25-move scrambles, after table generation:

| | min | median | mean | p95 | max |
| - | --- | ------ | ---- | --- | --- |
| solve time | 0.003s | 0.050s | 0.076s | 0.243s | 0.501s |
| solution moves | 19 | 23 | 22.4 | 23 | 23 |

## Usage

```bash
cd python
pip install -r requirements.txt
```

Solve a scramble:

```bash
cd src
python -c "
from cube import RubiksCube
from solvers.kociemba_solver import KociembaSolver

cube = RubiksCube()
cube.apply_algorithm(\"R U2 D' B D' F2 L2 R2 D' F' D2 B2 R2 U' L2 F2 U R2 D2\")

solver = KociembaSolver(verbose=True)
success, solution, nodes, seconds = solver.solve(cube)
print(' '.join(solution))
"
```

Or run any of the modules directly:

```bash
cd src
python demo.py                        # cube representation and moves
python -m solvers.kociemba_solver     # solve one scramble end to end
python -m solvers.kociemba_tables     # generate the lookup tables up front
python depth_wall.py                  # measure where BFS and A* stop working
python benchmark.py                   # compare all three solvers
```

Run the tests from the repository root:

```bash
python -m pytest python/tests
```

## Still planned

- **Iterative deepening A\* as a standalone solver.** The two-phase solver
  uses IDA\* inside each of its phases, but there is no single-phase IDA\*
  with a pattern database, and so no optimal solver: nothing here returns a
  provably shortest solution.
- **An interactive GUI.** The visualization is a static matplotlib net; there
  is no way to manipulate the cube or animate a solution.
- **Cubes other than 3x3.** `RubiksCube` rejects any other size.
- **A Java implementation.** None of this exists in Java yet.

## Technologies

- Python 3, with numpy for the sticker arrays and table generation, pandas for
  the benchmark output, and matplotlib for the visualization.
